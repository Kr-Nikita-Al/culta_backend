# WebSocket заказов

Оба пути находятся под префиксом `/order_websocket_router` из `main.py`:

- `/orders/ws/staff?company_id=<UUID>` — события выбранного заведения.
- `/orders/ws/client/<UUID>` — события собственного заказа клиента.

После открытия отправьте первым JSON-сообщением
`{"type":"authenticate","token":"<access_token>"}` в течение 10 секунд.
Токен не передаётся в URL. До успешной проверки подписка не регистрируется.
В production используйте WSS. Ошибки доступа закрывают соединение кодом 1008,
внутренние ошибки — 1011. Неверный UUID пути отклоняется до обработки заказа.

Access token должен иметь корректную подпись разрешённого алгоритма,
непустой `sub` и числовой срок действия `exp` в будущем. Заблокированный
или удалённый пользователь не получает доступ. Роли берутся из активных
назначений в БД, а не из клиентской команды.

Перед каждой командой и отправкой события повторно проверяются токен,
активность пользователя, роль в выбранной компании либо владелец заказа.
При потере доступа событие не отправляется, соединение закрывается с 1008.
У тихих соединений права проверяются раз в 30 секунд, срок токена — при
достижении `exp`. Сессии БД не удерживаются в ожидании входящих сообщений.
Ошибка повторной проверки БД не разрешает отправку данных (закрытие 1011).

Сотрудник получает `{"type":"ready"}` и может отправлять
`{"type":"update_status","order_id":"<UUID>","status":"processing"}`.
Обновление использует те же проверки ролей, переходов статусов и транзакцию,
что REST API. Ошибки команд возвращаются как `type: error` с `status` и `detail`.
События сотрудников: `new_order` и `order_updated` с полем `order`.

## Изоляция компаний

Подписки сотрудников хранятся отдельно по UUID компании. Каждое соединение
привязано к `company_id` из URL после проверки роли именно в этой компании.
При смене компании UI должен закрыть старое соединение и открыть новое
с повторной авторизацией; роль в одном заведении не даёт доступ к другому.
Если сотрудник работает в нескольких компаниях, каждая вкладка подписывается
только на выбранную компанию.

REST-уведомления о создании и изменении заказа используют компанию из заказа,
а не пользовательское поле команды. Менеджер отвергает событие, если компания
в данных заказа не совпадает с каналом рассылки или UUID обновляемого заказа
не совпадает с каналом клиента. При отказе данные не отправляются.

Регрессионные тесты проверяют два одновременных ASGI-соединения разных
компаний, REST-уведомления обоих типов, доступ по роли и ошибочную маршрутизацию.

## События клиента

Клиент получает `initial_status` с полями клиентского DTO, включая
`order_items`, затем `status_changed` с `order_id`, `status`, `order`.
Служебные комментарии и себестоимость товара в клиентские события не входят.
Текстовый `ping` получает текстовый `pong`.
При `completed`, `closed` или `canceled` отправляется `order_finished`,
после чего клиентские соединения закрываются кодом 1000. Для уже завершённого
заказа сразу отправляются начальное состояние и `order_finished`.

## Ограничения

- Менеджер хранит подписки в памяти одного процесса. Пока нужен один worker;
  для нескольких процессов/инстансов необходим общий pub/sub.
- Нет гарантированной доставки, истории событий или replay. После разрыва
  соединения следует заново получить состояние через REST.
- Отдельно остаются индивидуальный отзыв JWT-сессий и ограничения частоты
  сообщений. Здесь отзыв доступа означает деактивацию пользователя/роли
  либо изменение владельца заказа, а не отзыв конкретного JWT.
- UI пока использует REST и ручное обновление; подключение WebSocket к UI
  в эту правку не входит.
- Тесты используют настоящий ASGI WebSocket и подменённые операции БД.
  Реальная PostgreSQL и внешние сервисы в них не запускаются.
